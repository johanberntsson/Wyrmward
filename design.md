# WYRMWARD

## What this is

Wyrmward is a text adventure written in Inform 6 against the **PunyInform** library (not the standard Inform library). One source file, `wyrmward.inf` (~2800 lines), compiles to two targets from the same source: a plain **z5** story file and a **z6** build with graphics for 8-bit machines (Commodore/MEGA65, Commander X16) via Ozmoo.

## Build & test

All work goes through the `Makefile`, which hardcodes absolute paths to sibling checkouts. Adjust those variables rather than inlining paths.

```sh
make            # == make test
make test       # z5 build, run the regression transcript, open meld to diff
make z5         # inform +$(PUNY)/lib -v5 -es -D wyrmward.inf  -> wyrmward.z5
make frotz      # z5 build, then play interactively in frotz
make blorb      # resources/contents.yaml -> wyrmward.blb + converted pics/
make z6         # blorb, then -v6 build -> wyrmward.z6
make sfrotz     # z6 build, play in sfrotz (the --xscale/--yscale 2 flags are required)
make x16        # blorb + z6 + Ozmoo x16 packaging, launches x16emu
make mega65     # blorb + z6 + Ozmoo mega65 packaging, launches xemu-xmega65
make release    # z5 without -D (no DEBUG), then frotz
make clean
```

`-D` defines `DEBUG`, which enables the `cheat` verb (grants Animate + Teleport spells and jumps to `TeleportRoom`). `make release` omits it.

### The regression test is a transcript diff

There is no unit test framework. `make test` is the whole test suite:

1. `wyrmward.cmd` is a scripted playthrough fed to frotz on stdin. Its first commands are `transcript` + a blank line (accept the default filename), so the run writes `wyrmward.scr`.
2. `wyrmward.txt` is the **committed golden transcript**. `make test` opens `meld wyrmward.scr wyrmward.txt` so you can inspect the diff.
3. When a diff is an intended change, copy `wyrmward.scr` over `wyrmward.txt` and commit it alongside the `.inf` change. `wyrmward.scr` itself is gitignored; `wyrmward.txt` and `wyrmward.cmd` are tracked.

`wyrmward.cmd` contains `save`/`restore` pairs (each followed by a blank line to accept the default save name `wyrmward.qzl`), and `random seed 1` for determinism — keep both when editing it. `walkthrough.txt` is the minimal winning path; `aaa` is a scratch/partial command script, not part of the build.

Because a transcript diff catches every wording change, expect `wyrmward.txt` churn whenever room or object text is touched.

**`make test` needs a real terminal.** `frotz` is the curses build: run headlessly it emits escape sequences and `[MORE]` prompts to stdout and never creates `wyrmward.scr`, so the target silently produces nothing to diff. `dfrotz` is installed for that case — `dfrotz -w 80 wyrmward.z5 < wyrmward.cmd` replays the script to stdout — but its output carries a status line above every prompt and is not a drop-in substitute for the `.scr` transcript. Use it to check what the game *says*, not to regenerate the golden file.

`wyrmward.txt` also doubles as a design document. Editing the transcript by hand — fixing wording, inventing responses for commands the game does not handle yet — and then porting the result back into `wyrmward.cmd` and `wyrmward.inf` is an established workflow here. So a `wyrmward.txt` that does not match the current build is not necessarily stale: check whether it is running *ahead* of the source before "correcting" it.

### Editing the transcript by hand

When writing new prose or new commands directly into `wyrmward.txt`:

- **Hard-wrap at 80 columns.** The transcript is frotz output at `-w 80`; a longer line is immediately visible as a diff artefact. Check with `awk 'length($0)>80' wyrmward.txt`.
- **ASCII only**, for the same reason the `.inf` strings are (see the gotcha below). `LC_ALL=C grep -n '[^ -~]' wyrmward.txt` should print nothing.
- **Turn counts go stale.** `score` and the two end-of-game lines (`In that game you scored N out of a possible 50, in T turns.`) shift by one for every command added or removed. They are regenerated by the next `make test`, so approximating them is fine, but do not leave them obviously wrong.
- **Each command needs a distinct response.** A block of different commands all answering with the same stock line ("The beggar is fast asleep.") is the usual sign of a section that has not been written yet, and is normally the point of the exercise.
- Watch for the same object description being reachable under two nouns in one room (`x forest` / `x tree`, `x water` / `x mud`). In the transcript it reads as duplicated text; the fix belongs in the source, by giving one of them its own description.

### Prose conventions

The game's narration is British: `colour`, `odour`, `grey`, `metres`, `towards`, `draught`, `practised`, `goodwill`, `anti-clockwise`, `mouldering`. It uses Oxford `-ize` endings (`memorize`, `recognize`, `realize`), so those are not Americanisms. The one live inconsistency is `sulfur`, which is valid in both dialects and has been left alone deliberately — changing it would also need a `sulphur` dictionary word for the `x sulfur` command to keep working.

## Source layout of `wyrmward.inf`

The file is ordered deliberately; keep new code in the matching section.

1. **Compiler switches** (lines 1–5, must stay first): `-~S`, `$OMIT_UNUSED_ROUTINES`, `$ZCODE_LESS_DICT_DATA`, `$LONG_DICT_FLAG_BUG=0`, `$ZCODE_COMPACT_GLOBALS` — all for story-file size on 8-bit targets.
2. **PunyInform configuration**: the long block of `Constant OPTIONAL_*` toggles. Enabling one grows the story file, so they are enabled individually, not wholesale. `Include "globals.h"` comes after them.
3. **Entry points and `ParseName*` routines**, then `Include "ext_menu.h"`, `ext_cheap_scenery.h`, `LibraryMessages`, then `Include "puny.h"`. Order matters to PunyInform: config → `globals.h` → extensions/entry points → `puny.h`.
4. **z6 graphics block** (`#Iftrue (#version_number == 6)`): includes `ext_z6graphics.h`, defines `PIC_*` constants and `ShowPicture()`.
5. **Magic system** — spell/scroll classes and grammar.
6. **Custom verbs / grammar** and helper routines (`GrabObject`, `IsObjInContainer`, `ReplaceObj`, …).
7. **Rooms and their contents**, roughly in map order, each `Room` followed by its `Object ->` children.
8. **Portable objects** (scrolls, spells, stones, backpack, amulet), `Initialise`, the menu-driven help/hints, and `Epilogue`.

## Magic system

This is the core mechanic and the main thing to understand before editing.

- `CSpell` — a spell object; lives in `SpellBook` or inside a `CScroll`. `.number` tracks memorized copies against the global `no_memorized_spells` / `max_no_memorized_spells`. `CSpellWithArgument` subclasses it and requires a target.
- `CScroll` — a transparent container holding one spell; `CComplicatedScroll` is a scroll whose spell `CopySpell` refuses to copy (that is how the Resurrect spell is gated).
- `CSpell.activate(obj)` is the single funnel for casting. It handles the fish-form block (`player has general`), memorized-copy accounting, holding the spellbook, and the reading-from-scroll path, then calls `self.domagic(obj)`.
- **Targets react by providing `domagic`**, not by `before` rules: `domagic [spell; switch(spell) { HealSpell: ...; } ]`. Most spells start with `if(obj provides domagic) if(obj.domagic(self)) rtrue;` and fall through to a generic failure message. Returning true from `domagic` means "I handled it".
- **Rooms may provide `react_before_magic(spell, obj)`** — checked on `parent(player)` before `domagic` runs, to veto or intercept a cast in that location (used by the endgame force field).
- **Rooms may provide `react_after_magic(spell, obj)`** — checked on `parent(player)` after `domagic` runs, to perhaps add a comment from bystanders and the like (used in the village).
- Grammar: `cast <spell>` / `cast <spell> on <noun>` is the general form; `illuminate` and `copy` are direct verbs. The commented-out `Verb 'animate'`/`'freeze'`/`'heal'`/`'teleport'` blocks are deliberately disabled — the game now requires `cast`. `walkthrough.txt` still uses the old bare forms, while `wyrmward.cmd` uses `cast`.

## Dual z5/z6 targets

Every graphics call must be inside `#Iftrue (#version_number == 6); ... #Endif;` — the z5 build has no `ext_z6graphics.h` and no `PIC_*` constants. Room descriptions that show art call `ShowPicture(PIC_X)` guarded that way (see `RemoteHut`).

`ext_z6graphics.h` is a local PunyInform extension wrapping the v6 opcodes. Its central caveat, documented at the top of the file: v6 "units" differ per interpreter (Ozmoo reports 320x200 with a 4x8 or 8x8 font; sfrotz reports 640x400 with a 16x8 font). Never mix a unit value with a text row/column count — use the `*Cell` helpers (`Z6CursorRowCell`, `Z6MoveCursorCell`, `Z6PictureRows`) which convert through the font size. `ShowPicture` is written to be interpreter-agnostic this way, and no-ops when the picture id does not exist.

Picture ids come from `resources/contents.yaml`, consumed by Ozmoo's `make_blorb.py`. A `PIC_*` constant in the source must match an `id:` there. Inline room pictures set `height: 128` to leave room for text and the `[More]` prompt; the title picture omits it and fills the 320x200 screen. Source PNGs live in `resources/`; `pics/` holds the converted output and is gitignored, as are `wyrmward.blb`, `wyrmward.z5`, `wyrmward.z6`, and the packaged x16/mega65 images.

**Timed set pieces silently punish exploration.** The endgame `GateRoom` daemon runs a fixed five stages and then kills the player, so any scenery examined in that room costs a turn out of the five. When adding described scenery to a room on a timer, check that looking at it is still survivable.

The three daemon-driven set pieces are the cup game, the Dragon Hall and the Crypt. The intended direction (July 2026) is to make these **more forgiving** — either longer, or advancing only on real actions rather than on `examine`. So when writing new content for them, write what the scene needs and let the timing be adjusted afterwards; do not trim a response or drop a command because it would not fit in the current turn budget.

## Design intent that is not visible in the code

**The sleeping beggar is a gate, not a puzzle.** On the Country Road the beggar falls asleep until the hawker's stone has been won. The only purpose is to stop the player handing over the silver coin early, which would make the cup game unwinnable — or optional. The in-fiction excuse is deliberately mundane (he naps in the shade at the hottest part of the afternoon) and nothing wakes him: there is no solution to find. Responses there should read as "no reason to disturb him", not "he cannot be disturbed", so the player shrugs and leaves rather than grinding. Do not add hints, hidden causes or a way to wake him — that turns a piece of plumbing into a false puzzle.

More generally: a thin-looking obstacle may be load-bearing plumbing. Ask before enriching one.

## Conventions

- Locals in library-ish helper routines are prefixed `_` (`_rows`, `_i`); parameters in extensions use `p_`.
- Scenery with only a description uses the `cheap_scenery` property (word pairs + string) rather than separate objects; real objects are reserved for things with behaviour.
- Multi-word nouns that need flexible matching get a `ParseName*` routine near the top of the file rather than an inline `parse_name`.
- Score is awarded inline as `score=score+10` at plot milestones; `MAX_SCORE = 50`.
- `RemoveObj` / `ReplaceObj` exist so daemons and timers are stopped when an object leaves play — prefer them over a bare `remove`/`move` for objects that have a `daemon` or `time_out`.
